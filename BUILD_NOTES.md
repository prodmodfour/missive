`scripts/build-loop.sh` now cleans failed agent attempts by default: when the agent process fails, leaves the checkout dirty, or returns without a new commit, the loop resets to the pre-attempt `HEAD`, removes untracked non-ignored files with `git clean -fd`, waits 600 seconds, and retries the same cycle. The delay is configurable with `--failure-retry-sleep` or `MISSIVE_BUILD_LOOP_FAILURE_RETRY_SLEEP`; `--no-failure-retry` cleans once and exits. If the failed attempt log indicates a model token/context-length limit, the loop cleans the failed attempt, launches a splitter agent with reduced context files to split the current lowest TODO/IN_PROGRESS ticket into two smaller sequential tickets and commit that queue-only change, then retries after the same delay. `MISSIVE_SPLIT_AGENT_CONTEXT_FILES` customizes the splitter context, and `scripts/run-agent.sh` accepts `MISSIVE_AGENT_CONTEXT_FILES` for reduced-context agent launches.

`missive-core` exposes `MissiveError`, `Result<T>`, `ErrorCategory`, `MissiveExitCode`, and `ErrorReport`. The error taxonomy covers I/O, configuration, protocol, transport, storage, authentication, validation, and orchestration failures. Each category has a stable diagnostic code, deterministic exit code mapping for CLI use, human `Display` rendering, `miette::Diagnostic` metadata, and a serializable JSON/NDJSON report shape. `MissiveError::with_exit_code` allows command-specific deterministic exit codes, currently used by task wait and barrier: failed `80`, cancelled `81`, timeout `82`, and input-required `83`.

`missive-core` also exposes `AgentAlias`, `GroupName`, `RankName`, `TransportName`, `ContextId`, `TaskId`, `MessageId`, `EventId`, `MissiveTimestamp`, `Metadata`, `Envelope<T>`, and A2A metadata keys such as `a2a.protocol_version`. Named identifiers validate lowercase CLI-safe forms; opaque A2A/local IDs preserve server-provided text while rejecting empty, whitespace, control, or unbounded values. `Metadata` uses deterministic JSON object ordering, and `MissiveTimestamp` uses canonical RFC3339 UTC rendering.

The core configuration layer exposes `MissiveConfig`, `ConfigDiscovery`, `LoadedConfig`, and schema structs for profiles, agents, auth refs, storage, output, protocol service parameters, gateway, busy-input policy, routing defaults, adapters, and quality of service. Discovery precedence is `--config`, `MISSIVE_CONFIG`, repository-local config when `MISSIVE_REPO_CONFIG=1`, XDG config locations, then built-in defaults. Config parsing rejects unknown fields, validates cross references, rejects embedded credentials in URLs, rejects attempts to redefine reserved `A2A-Version`/`A2A-Extensions` service-parameter names in arbitrary parameter maps, validates built-in routing policy names in `routing.default_policy` and profile routing overrides, validates adapter kind/profile references and gateway/adapters busy-input policy values (`queue`, `interrupt`, `steer`) plus non-recursive steer fallback, validates env/keyring auth refs without accepting raw token values, provides redacted JSON rendering, and now has its selected profile `qos.max_request_bytes` enforced by send/stream message-part parsing and serialized A2A request-size validation.

The store path layer exposes `StatePathResolver`, `StatePaths`, `StatePlatform`, `StatePathSource`, `ProcessLockKind`, and `ProcessLock`. Runtime state defaults to XDG-compatible roots on Linux/Unix-like platforms, macOS `~/Library` fallbacks when XDG variables are absent, or `MISSIVE_HOME` when explicitly set. Paths include `profiles/<profile>`, relative database paths resolve under the selected profile state directory, and lock files live under `<state-dir>/locks/`.

The store migration layer exposes `Migration`, `AppliedMigration`, `MigrationReport`, `embedded_migrations`, `open_sqlite_database`, `migrate_database`, `migrate_connection`, `applied_migrations`, `schema_version`, `CURRENT_SCHEMA_VERSION`, and `SQLITE_APPLICATION_ID`. Migration SQL lives under `crates/missive-store/migrations`, is applied in version order inside transactions, and records checksums in `schema_migrations`. Schema version 1 creates tables for agents, contexts, tasks, messages, artifacts, events, groups, group_members, auth_refs, push_configs, gateway_jobs, and adapter_bindings; schema version 2 adds `gateway_sessions` for persistent source/agent/resume session context links and reset policy metadata.

The store repository layer exposes blocking `Store` and `StoreTransaction` APIs. `Store::open`, `Store::from_connection`, and `Store::open_in_memory` apply migrations before use. Typed methods cover non-secret auth refs, agents, contexts, tasks, artifacts, messages, events, groups/group members including group rename, push configs, gateway jobs, and gateway sessions with public upsert/insert/record structs, state/source/direction/role/artifact-kind/reset-mode enums, core identifiers, validated `GatewayJobId`/`GatewaySessionId`/`AdapterBindingId`/`ArtifactId`, JSON serialization at the repository boundary, A2A protocol-version metadata helpers for tasks/events plus message metadata storage, named session resume lookup by source kind/source id/agent/resume name, and transaction rollback on closure or SQL failures. SQL strings remain private to `missive-store` rather than leaking into CLI code. Raw auth tokens are not stored in SQLite; auth-ref rows contain only env var names or keyring service/account coordinates.

The A2A layer exposes the official `a2a-lf` protocol models through `missive_a2a::protocol`, aliases Agent Card/message/task/stream types to official SDK structs, provides `AgentCardClient`, `SendMessageClient`, `StreamMessageClient`, `TaskClient` with Get/List/Cancel/Subscribe operations, and `PushConfigClient`, includes interface negotiation helpers, centralizes A2A service parameters in `ServiceParameters`, and applies resolved auth headers through `AuthHeaders`. It resolves `/.well-known/agent-card.json` from a registered base URL, sends `A2A-Version` on every implemented HTTP request, optionally sends `A2A-Extensions` and validated extra service-parameter headers, marks auth header values sensitive before sending, sends conditional refresh headers when cached ETags/Last-Modified values exist, parses supported interfaces, provider, versions, capabilities, default modes, and skills through the official Agent Card type, maps HTTP/TLS/network failures to transport errors, maps invalid card JSON to protocol errors, and maps A2A `VERSION_NOT_SUPPORTED` responses to protocol errors with exit code 76. Non-streaming send maps `http+json` to `POST <interface>/message:send` with `application/a2a+json`, maps `json-rpc` to JSON-RPC method `SendMessage`, and parses direct `Message` and `Task` response shapes. Streaming send maps `http+json` to `POST <interface>/message:stream`, maps `json-rpc` to JSON-RPC method `SendStreamingMessage`, parses SSE `data` records incrementally, accepts direct or JSON-RPC-wrapped `StreamResponse` payloads, and rejects malformed stream events with protocol diagnostics that include the event sequence. Task operations map `http+json` to `GET <interface>/tasks/{id}`, `GET <interface>/tasks`, `POST <interface>/tasks/{id}:cancel`, and `POST <interface>/tasks/{id}:subscribe`, map `json-rpc` to `GetTask`, `ListTasks`, `CancelTask`, and `SubscribeToTask`, and parse official `Task`/`ListTasksResponse`/`StreamResponse` payloads; barrier remote polling reuses the same GetTask path per member task. Push config operations map `http+json` to `POST/GET/DELETE <interface>/tasks/{taskId}/pushNotificationConfigs[/<configId>]`, map `json-rpc` to `CreateTaskPushNotificationConfig`, `GetTaskPushNotificationConfig`, `ListTaskPushNotificationConfigs`, and `DeleteTaskPushNotificationConfig`, and parse official `TaskPushNotificationConfig`/`ListTaskPushNotificationConfigsResponse` payloads. Interface negotiation canonicalizes Agent Card bindings such as `HTTP+JSON` and `JSONRPC`, supports local `http+json` and `json-rpc`, recognizes gRPC for future extension diagnostics, respects agent binding preference or `agent inspect --binding`, and falls back to registry/base-URL interfaces when older cards omit `supportedInterfaces`.

`missive agent inspect <alias>` fetches and caches an A2A Agent Card when needed, applies configured and CLI-overridden A2A service parameters to the fetch, resolves and sends auth headers from agent config auth refs, `--bearer-token-env`, and repeatable `--header Name:Value`, negotiates the selected interface from `supportedInterfaces` and the agent binding preference, then renders the parsed provider, capabilities, skills, versions, supported interfaces, selected interface, and raw card JSON in machine output. `missive agent inspect <alias> --binding <binding>` requires a specific locally supported binding for advanced users/tests, `missive agent inspect <alias> --refresh` bypasses/revalidates the cache, and `missive agent refresh <alias>` explicitly refreshes the cached card. `missive agent capabilities [alias]` summarizes one or all registered agents for selection, fetching missing public Agent Cards, revalidating when `--refresh` is passed, and rendering local tags, Agent Card skill labels/tags, input/output modes, streaming support, push support, skills, and cache status.

`missive send <agent> [message]` sends one non-streaming A2A message to a registered agent. It supports positional text, `--stdin`, repeatable `--part text=...`, repeatable local file references through `--file`, repeatable raw byte attachments through `--file-bytes`, repeatable structured data parts through `--json-part`, repeatable MIME metadata through `--mime`, repeatable non-secret `--metadata KEY=VALUE`, `--context`, `--task`, repeatable `--accepted-output-mode`, and the existing global output/auth/service-parameter flags. Local file inputs are canonicalized to regular files with safe UTF-8 filenames, `--file` serializes as an A2A `url` file-reference part, `--file-bytes` serializes as an A2A `raw` part, JSON data parts default to `mediaType: application/json`, and both local inputs plus the serialized `SendMessageRequest` are bounded by the selected profile's `qos.max_request_bytes`. It uses the cached Agent Card when present, otherwise fetches and caches the public card before negotiation. It persists request and response rows in `messages`; direct `Message` responses are stored as response messages, and `Task` responses are upserted in `tasks` with remote task JSON, state, context/task linkage, protocol-version metadata, a linked response row, and redacted `a2a.send.request`, `a2a.send.response`, and task-update events where applicable. Machine output uses `kind: "send_result"` and includes request part summaries, response, selected-interface, and persistence summaries.

`missive stream <agent> [message]` sends one A2A streaming message to a registered agent. It shares the rich send input parser for text, file references, file bytes, JSON data, MIME metadata, and profile request-size limits, validates the Agent Card's `capabilities.streaming` unless `--force` is passed, negotiates HTTP+JSON or JSON-RPC, opens an SSE response, renders one human/NDJSON update per parsed event as it arrives, and emits a final `stream_result` summary. The outbound stream request and each parsed `task`, `message`, `statusUpdate`, or `artifactUpdate` are appended to the SQLite event journal with event types under `a2a.stream.*`; parsed remote stream updates are also stored as `messages` rows with direction `stream_event` and linked to task/context rows where IDs are present. Status and task events update the local task state and completion timestamp for completed/failed/cancelled states. Task events persist embedded artifacts, and `artifactUpdate` events upsert dedicated artifact rows, merging appended chunks and incrementing the local artifact version.

`missive task` now implements `get`, `list`, `wait`, and `cancel`. Local `task list` filters SQLite task rows by agent, context, state, updated-after timestamp, and source (`remote`, `local`, or `gateway`). `task get` reads a local row by default or refreshes it with A2A `GetTask` when `--remote` is passed. ## Limitations

The property-based tests added in ticket 055 are bounded randomized checks that run in the normal Rust test pass; they improve parser/router invariant coverage but are not a formal proof of all possible inputs. When a property fails, rely on the minimized failing input and reproduction details printed by `proptest` before deciding whether to add a stable regression seed.

The fuzz targets added in ticket 056 are bounded parser/replay smoke targets, not continuous fuzzing campaigns. The default documented and quality-gate path uses `--sanitizer none` so it works with the stable toolchain; sanitizer-backed campaigns should be run separately with a compatible nightly setup and `MISSIVE_FUZZ_SANITIZER=address`. Generated corpora, target directories, coverage output, and crash artifacts must stay out of commits unless a future bug fix intentionally adds reviewed regression seeds.

The mutation path added in ticket 057 is a bounded smoke/check workflow and a focused failure-injection suite, not a full mutation-testing campaign. `scripts/mutation-smoke.sh` defaults to `cargo mutants --check` on a shard of critical files; use `MISSIVE_MUTANTS_MODE=run`, wider shards, and longer timeouts for local campaigns. Generated `mutants.out/` and temporary `missive-mutants.*` output must stay out of commits.

The benchmarks added in ticket 058 are local Criterion probes and soft performance-budget guidance, not an enforced regression gate. The default quality gate runs the Criterion harness in test mode through `cargo test --all-targets`; aggressive mode compiles benchmarks with `cargo bench --no-run`; full measurements and saved-baseline comparisons remain manual. Generated Criterion output under `target/criterion/` must not be committed.

The CI workflow added in ticket 059 is intentionally Linux-only and mirrors the local default quality gate; cross-platform matrices are deferred to ticket 060. Optional coverage is a smoke check that runs only through manual dispatch or a non-secret repository variable and does not publish reports by default.

The command examples under `examples/` are local smoke demos, not an interoperability or production operations suite. By default they require Bash plus Cargo unless `MISSIVE_BIN` and/or `MISSIVE_EXAMPLE_A2A_BASE_URL` are provided, create temporary runtime state under `MISSIVE_HOME`, and exercise the local mock A2A fixture rather than an independent remote A2A implementation. They intentionally cover agent registry, send, stream/task, context/group/route, and gateway lifecycle commands only; broader push/webhook/collective/end-to-end demos remain for their later tickets.

The A2A conformance fixture suite is a static, local compatibility suite based on A2A 1.0 specification examples and the current official Rust SDK wire shape. It is not an external certification program and does not prove interoperability with every independent A2A implementation; ticket 066 remains responsible for running against an upstream/example A2A agent.

`missive-test-support` remains a deterministic local fixture server rather than a formal external conformance service. It intentionally serves the endpoint shapes needed by current and near-future missive tests.

Older CLI integration tests still contain some per-file minimal TCP mocks from earlier tickets. New protocol/gateway/push/adapters tests should prefer `crates/missive-test-support`, and legacy mocks can be migrated opportunistically when those tests are touched for functional work.

`missive task` implements direct foreground task get/list/wait/cancel. Gateway-managed task monitoring now exists in `missive gateway run` for cached streaming-capable agents, and background waits can be enqueued with `missive job start wait`; the `task` CLI itself does not attach to gateway jobs or update task state from webhook callbacks yet.

Remote `task list --remote` is scoped to one agent and one response page. It accepts `--page-size` and `--page-token`, renders the returned `nextPageToken`, and persists returned tasks, but it does not auto-page through every remote task yet.

`task wait` uses blocking polling in the current CLI process. It does not subscribe to remote task updates, cancel an in-progress wait on local input, or coordinate with gateway jobs. Non-success wait states intentionally render the final task output on stdout first and then return a structured error on stderr with exit codes `80` through `83` for shell automation.

`task cancel` calls the remote A2A agent and requires either `--agent` or an existing local task row from which an agent alias can be resolved. There is no local-only task cancellation/marking mode yet.

Task commands persist raw remote task JSON in the `tasks.remote_task_json` column, matching earlier send/stream task persistence. Normal human/JSON/NDJSON command output is redacted before printing, but local SQLite state should still be treated as potentially sensitive runtime data and kept outside the repository.

Task artifacts are persisted and exportable only after an implemented command has observed them in a `Task` payload or streaming `artifactUpdate`. `missive task artifact` and `missive gather --output-dir` do not call remote A2A endpoints themselves, auto-refresh missing artifacts, fetch URL/file-reference artifact contents, prune old artifact versions, or store large byte payloads outside SQLite yet. URL/file-reference artifacts export as JSON manifests rather than dereferencing potentially untrusted locations.

`missive context` is local control-plane state only. It does not call a remote A2A context-close endpoint, synchronize named contexts with agents, merge/fork remote context history, or expose gateway session resume/reset commands; those remain for later protocol/gateway/session tickets.

Context names are accepted by `context show/fork/close/export` only when they uniquely identify one local row. `send`, `stream`, and `task` still accept explicit A2A context ids rather than context names; use `missive context show <name> --json` to resolve a name to an id for automation.

`context export` includes linked task, message, and event rows and redacts normal stdout/stderr output, but it does not yet include dedicated artifact rows/files, push configs, adapter bindings, gateway jobs, event replay summaries, or retention/pruning metadata. Local SQLite state can still contain raw remote protocol payloads before export-time redaction and must stay outside the repository.

`missive group` CRUD is local control-plane state only. It validates routing policy labels and stores group membership but does not route messages or run collectives by itself. `group capabilities` can fetch/revalidate public Agent Cards for member summaries, but those summaries are not persisted as separate rows beyond the normal Agent Card cache. `missive route explain` can dry-run routing decisions over stored groups, and `missive bcast` consumes stored group membership for non-streaming broadcast sends. `group add` requires registered agent aliases already present in the selected profile store, and group metadata/routing metadata should remain non-secret because local SQLite state is not encrypted by missive.

`missive route explain` is a dry-run planner only. It does not send A2A messages, persist route decisions, persist round-robin cursors, update group/member state, or run collectives. Capability-match uses cached public Agent Cards by default and only performs public Agent Card fetch/revalidation when `--refresh-capabilities` is explicitly passed; if no cached card exists, card-derived requirements such as streaming, push, or media modes are reported as unknown in `missing_requirements`. Capability scoring is deterministic and local; it is not a latency, cost, health, or quality-of-answer ranking.

`missive bcast` implements non-streaming broadcast only. It does not stream member responses, cancel already-started concurrent worker threads after another member fails, derive routing/capability policy decisions, or refresh member capabilities before sending. Use `missive route explain` to inspect a dry-run route plan, `missive barrier` to wait for returned member tasks, `missive gather` to collect local outputs/artifacts, and `missive reduce` to produce a final source-attributed result.

`missive barrier` synchronizes known task state only. It does not create broadcasts, discover tasks from remote agents without either local task rows or `bcast_result` task ids, subscribe to task streams, collect outputs/artifacts itself, cancel failed/pending tasks, update gateway jobs, or run reductions. Missing member task rows remain pending until timeout unless a smaller quorum is satisfied.

`missive gather` is local-only output collection. It does not refresh remote task state, subscribe to task streams, fetch missing remote artifacts, include direct message responses that never created task rows, compress/export whole contexts, or reduce outputs by itself; run `missive barrier`, `missive task get --remote`, or `missive task list --remote` first when the local store needs fresher task payloads.

`missive reduce` is local-source reduction: it reads already persisted local group task/message/artifact rows and does not refresh remote tasks, subscribe to task updates, fetch artifact contents, or include direct message responses that never created member task rows. Local `summarise` is deterministic source-attributed formatting rather than semantic LLM summarization; use `--reducer-agent` or `--command` for richer reducers. `--command` runs a user-supplied local shell command without sandboxing or timeout enforcement, and reducer-agent calls currently use the default blocking SendMessage client timeout rather than the global `--timeout` budget.

`missive stream` implements initial A2A `SendStreamingMessage` only. Task resubscription/`SubscribeToTask` is implemented in the gateway daemon for locally persisted in-flight tasks, but the stream CLI does not attach to gateway-managed streaming jobs, resume a foreground stream after process restart, or support local user-triggered cancellation of an active stream.

`missive adapter stdio` is a foreground subprocess loop only. It maps JSON/NDJSON frames to existing send, stream, and task commands in the current process, but it does not start from `missive gateway run`, persist adapter bindings, maintain gateway sessions, apply busy-input queue/interrupt/steer policy, multiplex concurrent requests, or provide a separate stdin body channel for `--stdin`; message content must be carried in frame fields such as `message`, `text_parts`, or `json_parts`. In single-shot JSON mode, stream output is wrapped as one final JSON `stream_result`; use long-running NDJSON mode for one wrapped `stream_event` frame per remote stream event.

`missive adapter file-drop` is a foreground filesystem polling loop only. It does not start from `missive gateway run`, persist adapter bindings, apply busy-input queue/interrupt/steer policy, run OS-native file notifications, or prevent a producer from writing partial content directly to a final `*.json` name. Producers must write temporary files and atomically rename complete requests to ready `*.json` names. Command execution errors are returned in wrapped result frames; malformed or unparseable request files are archived to the error directory with `file_drop_error` output. Inbox, outbox, processed, and error directories are local runtime state and may contain message text, source ids, job requests, and command outputs, so keep them outside the repository.

`missive gateway run --http-adapter` is an ingress/event-bus endpoint only. It validates `missive.http.v1` JSON, optional header-token auth, body size, and process-local rate limits, then journals and emits accepted frames as adapter events; it does not yet execute submitted send/stream/task frames, create or reset gateway sessions, persist adapter bindings, invoke busy-input queue/interrupt/steer policy, enqueue background jobs from HTTP, or provide production-grade public API hardening. Keep it bound to loopback or behind trusted local infrastructure, and treat accepted/rejected event rows as local runtime data that can include redacted source/message history.

External chat adapter kinds for Discord, Slack, Telegram, Matrix, and Email are feature-gated compileable stubs only. They register placeholder factories when enabled and can map external identities for tests/design work, but they do not start live platform clients, poll or receive third-party events, validate platform signatures, manage OAuth/webhook setup, request platform scopes, deliver outbound updates, or send on-platform acknowledgements. Adapter settings for these stubs must remain non-secret references and public routing hints; real platform tokens, signing secrets, mailbox credentials, private workspace names, private email addresses, and private homeserver URLs must not be committed.

`missive send`, `missive stream`, `missive adapter stdio` send/stream frames, `missive adapter file-drop` send/stream request files, HTTP adapter send/stream frames, and `missive bcast` now support text, local file-reference, raw file-byte, JSON data, and MIME-aware message parts, but they still do not implement streaming/chunked file upload. Local file inputs larger than selected-profile `qos.max_request_bytes` fail locally instead of being streamed. `--file` sends a canonical `file://` URL and can reveal the local path to the remote agent and in local SQLite request-message rows; use `--file-bytes` only for content you are willing to embed in the A2A request.

`--mime` assignment is deterministic but grouped by missive's part-building order rather than the user's shell flag order across different repeatable flag kinds. One value applies to all non-text file/JSON parts; multiple values must match either the non-text part count or total part count.

`missive push` configures remote A2A task push notification configs and persists redacted local records, and `missive webhook run` can receive the resulting callbacks locally, but missive does not rotate callback credentials, auto-refresh push configs in the background, verify webhook signatures/JWTs, or use push events to update task state yet. Those behaviors remain for later gateway/security tickets. `push list` is scoped to one task/agent response page and records returned `nextPageToken`, but it does not auto-page through every remote config.

`missive logs` is a local diagnostics inspection surface, not a health checker and not a universal log collector. Foreground commands still write diagnostics to stderr unless an operator or supervisor redirects them; missive only reads profile log files under `<profile state dir>/logs/` and reports event-journal/gateway-service hints rather than streaming journald/launchd logs directly. The command does not validate endpoint reachability, database migration health, gateway status, log rotation, retention, external sinks, or tool availability; use `missive doctor` for health checks and later operations tickets for broader diagnostics.

`missive doctor` now contacts only config-seeded A2A agent base URLs with safe public Agent Card discovery requests and probes only the selected local gateway `/status` URL. It does not inspect agents that exist only in the SQLite registry, auto-page remote status APIs, send mutating protocol requests, query gateway `/healthz` separately, inspect systemd/launchd runtime state, migrate databases, create missing profile databases, verify log rotation/retention, or install missing tools. Existing SQLite databases are opened only to inspect schema version and migration ledger state; missing databases are reported as skipped because stateful commands create and migrate them when needed. If no config-seeded agents or enabled/running gateway are present, doctor reports those checks as skipped/not applicable without failing the run.

`missive events` reads the local SQLite journal only, including gateway subscription events when the daemon is running. It does not itself subscribe to remote A2A task updates, reconstruct full protocol objects from incomplete event streams, replay side effects, prune old events, compact snapshots, or export to external observability systems. `events tail` uses polling and must be bounded with `--limit`, global `--timeout`, or process control in non-interactive automation.

`missive gateway run` supervises the event bus, store initialization, local health/readiness/status endpoints, optional HTTP inbound adapter endpoint, persistent session store readiness, task subscription/resume worker, background job manager, and adapter event-bus bridge. The subscription worker requires cached Agent Cards that advertise streaming, updates task state from task/status events, and records artifact/message subscription events in the journal, but it does not yet persist subscribed messages/artifacts as dedicated rows. The background job manager executes queued `send`, `stream`, `wait`, and deterministic local `reduce` jobs and stores result JSON, but it does not yet persist every streamed message/artifact as dedicated rows, call reducer agents or local command pipelines, embed the webhook receiver, or start configured stdio/file-drop/external adapters. External adapter workers have only registry stubs today. Gateway sessions are persisted and reset policies are evaluable, but no CLI or adapter path automatically creates, resumes, rotates, or announces session resets yet. The `/healthz`, `/readyz`, and `/status` endpoints are unauthenticated local HTTP endpoints intended for loopback supervision; the HTTP adapter endpoint is authenticated only when `--http-adapter-auth-token-env` is configured.

Busy-input queue/interrupt/steer behavior is currently a shared policy evaluator and validated config schema for gateway/adapters. Background job cancellation can mark local job rows and the foreground CLI can request remote A2A `CancelTask`, but no current adapter/inbound source invokes the busy-input evaluator automatically, persists queued busy inputs, or cancels foreground waits from another process. Future adapter workers must execute the returned actions and keep any queued input in profile state outside the repository.

`missive gateway install/start/stop/status/uninstall` manages service files and supervisor commands only for Linux systemd and macOS launchd. Other platforms return a clear unsupported-platform diagnostic and should run `missive gateway run` under an external supervisor. Service installation does not yet provide package-manager integration, enable/disable autostart commands, privilege escalation, log rotation, OS-specific hardening sandboxes, or a remote control socket; use `--dry-run` to inspect generated files before writing them.

The `--timeout` global flag now drives `missive task wait`, `missive job start wait` request timeout storage, `missive bcast` Agent Card/member send calls, `missive barrier` polling, graceful `missive webhook run` shutdown, and graceful `missive gateway run` shutdown, but it still does not drive standalone send/stream HTTP client timeout construction or general command cancellation. `missive job start --attach` has its own `--attach-timeout`. The streaming/client layers currently use the A2A layer's default blocking reqwest timeouts for non-wait network calls.

Authentication is wired into implemented Agent Card fetch/refresh, doctor endpoint checks, non-streaming send, broadcast sends, barrier remote task polling, reduce reducer-agent sends, streaming send, remote task, push config HTTP paths, `missive job cancel --remote`, the inbound webhook header-token hook, and the inbound HTTP adapter header-token hook. Gateway subscriptions and gateway-executed background send/stream/wait jobs currently send configured A2A service parameters but do not yet resolve outbound auth refs, keyring entries, `--bearer-token-env`, or `--header` values, so authenticated remote subscription resume and authenticated gateway jobs remain limitations; future gateway worker behavior, adapters, collectives, and observability must reuse the same auth/redaction path when they add broader network calls.

Keyring-backed auth refs can be resolved when the `native-keyring` feature is enabled and the local platform/session keyring is available, but missive does not yet provide commands to create, update, list, or delete keyring entries. Users must provision those entries with OS tooling or another keyring client. Builds without `native-keyring` parse keyring refs but fail clearly if one is needed.

There is no local-only insecure raw-token storage mode. SQLite auth-ref rows intentionally store only env var names or keyring service/account coordinates. If an insecure mode is ever added, it must be explicit and documented in a later security/storage ticket.

Config-seeded agents are synced into SQLite as read-only rows when agent/send/stream/task/context/group/route/bcast/barrier/gather/reduce/job commands run, including capability summary and route refresh paths. If a config entry is later removed, an already-synced row may remain in the local database until a future reconciliation/maintenance command defines stale config-seed pruning. Cached Agent Card fields are preserved only while the config-seeded base URL remains unchanged.

The `missive` binary has a real command tree, global parser, configuration discovery/profile validation, A2A service-parameter flags, auth input flags, output rendering contract, shell completion generation, manpage generation, foreground stdio adapter frame loop, foreground file-drop adapter inbox/outbox loop, opt-in gateway HTTP inbound adapter endpoint, implemented agent registry commands, Agent Card inspection/refresh/capability summaries, selected-interface negotiation, non-streaming send, capability-aware route explain, broadcast collective, barrier collective, gather collective, reduce collective, streaming send, task get/list/wait/cancel, task artifact list/show/save/export, context create/list/show/fork/close/export, group create/list/show/capabilities/add/remove/rename/delete, push create/get/list/delete, webhook run, gateway run with subscription/resume, background jobs, adapter event-bus bridge, and session-store readiness, gateway service install/start/stop/status/uninstall, job start/list/show/cancel, doctor, logs, and events list/tail/replay/export. Daemon-started stdio/file-drop/external adapters and live external chat platform clients remain for later tickets.

`missive completion` generates static shell completion scripts from the local clap command tree only. It does not provide dynamic completion of local agent aliases, context names, task ids, or group names from the SQLite store. `missive manpage` emits the root `missive(1)` roff page; it does not install the page automatically or emit separate per-subcommand manpage files yet.

The store layer resolves state paths, provides process locks, migrates fresh SQLite databases to schema version 2, and exposes typed repository APIs for auth refs, agents, contexts, tasks, artifacts, messages, events, groups, group members including group rename, push configs, gateway jobs, and gateway sessions. Route explain, bcast, barrier, gather, reduce, and background job commands currently reuse existing agent/group/context/task/message/artifact/event/gateway-job repositories rather than adding new tables. Adapter-binding repositories, retention enforcement, compaction, automatic gateway session lifecycle producers, future adapter event producers, and broader durable A2A protocol persistence remain for later tickets.

The store repository is synchronous because it uses `rusqlite`; async gateway/adapter code should call it through a blocking task or store worker when those tickets wire runtime behaviour.

The config schema includes protocol, auth refs, gateway, busy-input, routing, adapter, and QoS defaults. Effective `routing.default_policy` is used by `missive route explain` for ad-hoc explicit-agent routes when no CLI policy or group policy applies. Selected-profile `qos.max_request_bytes` is enforced by send/stream/job-start/message-part parsing including stdio adapter send/stream frames, file-drop send/stream/job request files, and serialized request-size validation, `gateway.bind_address` seeds `missive webhook run` plus `missive gateway run`, and `gateway.job_concurrency` is reported by the gateway daemon and used to bound each background job scan. `[adapters.<name>]` entries can be converted into `AdapterDefinition` rows by `missive-adapters`, including non-secret file-drop path settings and feature-gated external stub kinds, and `[gateway.busy_input]` plus `[adapters.<name>.busy_input]` are validated and available to gateway/adapter workers through `LoadedConfig`, but current CLI commands do not expose busy-input controls. Agent capability summaries and `route explain --refresh-capabilities` use the effective A2A service parameters and outbound auth resolution when fetching public Agent Cards. Gateway subscriptions and background jobs use the effective protocol service parameters, but other gateway/adapter/QoS values do not yet enforce foreground send/stream HTTP timeouts or start daemon-managed adapters.

The `--json`, `--ndjson`, and `--quiet` flags override config output defaults. `--config`, `--profile`, `--protocol-version`, `--a2a-extension`, `--service-param`, `--bearer-token-env`, and `--header` are active for implemented Agent Card inspect/refresh/capability-summary, doctor endpoint checks, route capability refresh, send, bcast, barrier, reduce reducer-agent, stream, remote task, push config paths, and `job cancel --remote`; `job start send/stream/wait` records effective service-parameter metadata for gateway execution; `webhook run` uses `--protocol-version` as event metadata fallback and `--timeout` as a shutdown budget; and `gateway run` uses `--protocol-version`/A2A service-parameter flags for subscription/background-job calls plus `--timeout` as a shutdown budget. `gateway run` and installed gateway services do not yet apply global outbound auth flags to subscription or background-job calls. The `--trace`, `--verbose`, and `--no-color` flags now feed stderr diagnostics through `missive-observe`; `RUST_LOG` takes precedence over verbosity defaults and `MISSIVE_LOG_FORMAT=json`/`MISSIVE_LOG_JSON=1` switch logs to JSON lines without changing stdout output modes.

Redaction is active at the config and CLI output boundaries for structured values rendered through the current helpers, and `AuthHeaders` debug output is redacted. The `missive-observe` log formatter also redacts secret-like field names, authorization/cookie/token/password/API-key fields, common auth-scheme text, and secret-like key/value fragments before writing human or JSON logs to stderr. Current event journal producers redact payloads before insertion; group event persistence stores only redacted local group/member payloads, broadcast, barrier, gather, and reduce event persistence stores redacted group operation/member/provenance summaries, push config persistence also stores redacted `remote_config_json` for callback authentication credentials, webhook persistence redacts token-like callback fields and rejection payloads, gateway lifecycle persistence stores only local non-secret status payloads, gateway subscription persistence redacts stream/retry payloads before journal insertion, gateway HTTP adapter accepted/rejected events redact token-like request fields before journal insertion, and gateway job persistence redacts lifecycle/event payloads while job command output summarizes request rows instead of echoing raw A2A requests. Adapter trait events are serializable and should carry non-secret metadata; foreground stdio adapter output wraps the same redacted CLI JSON/NDJSON envelopes for command results and errors, foreground file-drop output writes the same wrapped envelopes into local outbox result files, and gateway HTTP adapter runtime output is passed through the same redacting output renderer. `gateway_jobs.request_json` can still contain full queued message content and file bytes so the daemon can execute later; file-drop inbox/outbox/archive directories can also contain full request/result content; local SQLite state and local adapter directories must remain outside the repository and be treated as sensitive. `doctor` plus `logs` plus `context export` plus `events list/tail/replay/export` redact linked local diagnostic/log/task/message/event payloads before printing. Operation-level spans now carry safe identifiers, bindings, states, counts, and sanitized endpoint context, but storage retention/compaction policy, external event/log sinks beyond stderr/service-manager capture, signature/JWT verification, production-grade rate limits, service-manager hardening policies, and broader daemon adapter trust-boundary enforcement remain for later security and observability tickets.

Optional exhaustive validation tools are not all installed in this environment yet. The default quality gate passes without them and uses installed optional tools automatically. `cargo-nextest` is currently missing, and miri is unavailable for the active stable toolchain.

There is not yet a `cargo-deny` policy file; the quality gate skips deny checks until the supply-chain policy ticket introduces one.
